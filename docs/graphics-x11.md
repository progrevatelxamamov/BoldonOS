# Графика и Xorg: первый, аппаратно-независимый этап

BoldonOS пока использует framebuffer, полученный от Limine. `/dev/fb0` даёт
прямой доступ к нему; `/dev/dri/card0` сегодня **только старый псевдоним
fbdev**, а не DRM/KMS. В частности `FBIO_WAITFORVSYNC` пока не ждёт
настоящего vblank; нельзя называть этот путь синхронизированным или
гарантировать 60 кадров/с без разрывов.

Для диагностики на любом из ПК: `cat /dev/gpuinfo`. Файл перечисляет все
обнаруженные PCI-видеоконтроллеры (до восьми), выводит BDF, vendor/device ID,
subclass, revision, размер и pitch начального framebuffer. Это **только
чтение PCI config space** и параметров Limine — никаких изменений в GPU,
видеорежиме или в рабочих USB/дисковых драйверах. Список не ограничен
определённой моделью CPU; пустой список возможен и при рабочем framebuffer.

На хосте с **Ubuntu** нет готовой конфигурации репозиториев и ключей Arch
Linux для `pacman`: одной установкой `pacman` через apt это не исправить.
Если нужен именно Arch Xorg в `osdata/`, можно использовать Arch-контейнер
(требуются Docker и доступ к образу `archlinux:latest`). Перед этим
сохраните резервную копию существующего `osdata` — установка пакетов может
конфликтовать с уже положенными туда файлами. В WSL запускайте установку
из файловой системы Linux (например, `~/BoldonOS`), **не** из `/mnt/c/...`:
Windows-раздел через DrvFs может показывать каталоги как `777`, игнорировать
нужные Unix-права и вызывать тысячи предупреждений pacman `filesystem: 777,
package: 755`. Хуже того, при регистронезависимой настройке NTFS пути
`/usr/lib/Xorg` (исполняемый файл) и `/usr/lib/xorg` (каталог модулей)
совпадают: установка завершается `not overwriting dir with file` и не может
быть исправлена `--overwrite '*'` или удалением каталога модулей. Проверка:
`stat -c '%i %n' osdata/usr/lib/Xorg osdata/usr/lib/xorg` покажет одинаковый
inode в случае коллизии. Перенесите рабочую копию вместе с `osdata` на
файловую систему Linux внутри WSL перед повторной установкой. Уже
скопированные из DrvFs права могут оставаться неверными — проверяйте их
отдельно. `main.img` копирует права из дерева, поэтому одного подавления
предупреждений недостаточно. Для уже установленного дерева
сначала проверьте результат и права, не применяйте `chmod -R 755` (это
сломает, например, `/tmp` и обычные файлы).


```sh
mkdir -p osdata/var/lib/pacman osdata/var/log
sudo docker run --rm -it -v "$PWD/osdata:/rootfs" archlinux:latest sh -ec '
  pacman --root /rootfs --dbpath /rootfs/var/lib/pacman \
    --logfile /rootfs/var/log/pacman.log --config /etc/pacman.conf \
    --gpgdir /etc/pacman.d/gnupg --cachedir /var/cache/pacman/pkg \
    -Syu --needed xorg-server xorg-xinit xf86-video-fbdev xf86-input-evdev xterm
'
```

`-it` сохраняет терминал и ввод для подтверждения `[Y/n]`: без `-i`
`pacman` получит EOF и выйдет, не установив пакеты. `--root` направляет
файлы в `osdata/`; явные `--dbpath` и `--logfile` гарантируют, что база и
журнал также останутся в нём, а не в контейнере. `--cachedir` хранит архивы
только внутри временного контейнера. Перед подтверждением списка обновлений
проверьте `osdata/var/lib/pacman/local`: если каталог пустой, но pacman
показывает *старые версии* системных пакетов, не подтверждайте установку —
проверьте путь базы пакетов. Не применяйте `--overwrite '*'` для разрешения
конфликтов с существующими файлами. Сборка `main.img` копирует `osdata/` в
ext4 при **новой сборке** образа (не изменяет готовый образ); проверьте,
что в разделе хватает места для пакетов. Это способ подготовки бинарников,
а не готовый установщик или гарантия работоспособности Xorg в BoldonOS.

**Установка не означает, что Xorg уже запустится.** `startxfce4` и
`/etc/X11/xinit/xserverrc` — shell-скрипты с `#!`: `execve` должен передавать
их интерпретатору. Раньше ядро принимало только ELF, а системный вызов
ошибочно превращал все ошибки `execve` в `EPERM` («Operation not permitted»).
После поддержки скриптов ошибки Xorg нужно диагностировать по настоящему
коду возврата и его журналу; исправление `execve` само по себе не добавляет
DRM/KMS. Это бинарники Arch Linux,
а не портированный X-сервер: они зависят от ABI Linux, динамического
загрузчика, поддерживаемых системных вызовов, устройств ввода и корректных
fbdev/DRM ioctl. Драйвер `xf86-video-fbdev` — лишь программный запасной
вариант, не обеспечивает KMS, аппаратную акселерацию и vsync. Если сервер
выбирает `/dev/dri/card0` как настоящий DRM-узел, он получит несовместимые
ioctl; его нельзя считать реализацией DRM.

### Wayland на Arch-хосте и гостевые системные вызовы

Plasma на **хосте** не предоставляет BoldonOS DRM/KMS: при загрузке BoldonOS
её `/dev/dri/card0` остаётся fbdev-псевдонимом без настоящего vblank. Установка
или запуск `startplasma-wayland` в гостевой файловой системе — проверка ABI,
а не свидетельство, что Plasma 6 уже может вывести кадр.

Для проверки ABI добавлены x86-64 Linux-вызовы `sched_getaffinity` (204),
`madvise` (28), `ppoll` (271), `getpeername` (52). `sched_getaffinity`
возвращает маску **реально включённых** логических CPU. `madvise` принимает
только подсказки NORMAL/RANDOM/SEQUENTIAL/WILLNEED; DONTNEED/FREE/REMOVE
возвращают `ENOSYS`, поскольку фиктивный успех там изменил бы семантику
памяти. `ppoll` использует миллисекундный таймер и округляет положительные
доли миллисекунды вверх; сигнальная маска пока хранится **на уровне процесса**,
поэтому атомарная семантика маски при нескольких потоках не соответствует
Linux. UNIX `getpeername` возвращает адрес соединённой стороны с учётом
размера буфера. Следующие ошибки запуска следует диагностировать отдельно;
этот ABI-этап не реализует дисплейный драйвер, seat или Wayland-композитор.

При запуске `startplasma-wayland` через `plasma-dbus-run-session-if-needed`
следующий наблюдаемый блокер — `dbus-daemon: Unable to create reload pipe:
Could not create full-duplex pipe`: вызов 53 — `socketpair`, **не** `pipe2`.
Для `AF_UNIX/SOCK_STREAM` добавлена настоящая пара соединённых сокетов с
двусторонним чтением/записью, обратным давлением, EOF после закрытия второй
стороны и поддержкой флагов NONBLOCK/CLOEXEC. `close_range` (436) закрывает
существующие FD для `flags=0`; режимы UNSHARE/CLOEXEC не выдаются за
реализованные. `inotify_init1` (294) и `inotify_init` (253) теперь
создают читаемый/pollable дескриптор с реальной очередью событий; `add_watch`
(254) и `rm_watch` (255) отслеживают операции VFS (создание/удаление,
чтение/запись, открытие/закрытие). Пока нет событий от обходящих VFS
операций, переименования и `IN_EXCL_UNLINK`; `IN_ONESHOT` и
`IN_DONT_FOLLOW` поддержаны. Ограничение — 64 watch и 64 события на
экземпляр. `pidfd_open` (434) теперь выдаёт FD с готовностью `poll`
при завершении или сборке процесса (без `pidfd_send_signal`/`waitid(P_PIDFD)`).
`capget` (125) поддерживает версии Linux v1/v2/v3 и сообщает **только**
реально действующие в BoldonOS права root: DAC_OVERRIDE, SETUID, SETGID;
полной модели Linux capabilities и `capset` здесь нет. Предупреждение Qt об ANSI locale
отдельно от сбоев D-Bus; `LANG=C.UTF-8` убирает его, но не создаёт DRM/KMS.

### Если Xorg ждёт без журнала

`/dev/xorgtrace` — ограниченный снимок (последние 64 события) этапов
`execve` для `/usr/bin/X`, `Xorg.wrap`, `Xorg` и системных вызовов процесса
Xorg. `exec.begin`, `exec.open`, `exec.interp`, `exec.entry`, `exec.fail`
показывают, как далеко дошла загрузка; `exec.fail` содержит номер ошибки
в `a1`. `syscall` содержит номер Linux-вызова `num`, два первых аргумента
и результат в hex; `pending=1` означает, что вызов ещё не вернулся.
Из `xinit` пишутся только попытки создать дочерний процесс или исполнить
программу, чтобы ожидание сервера не забивало буфер. Первые 12 этапов
`execve` и ограниченная выборка вызовов (первые 12, затем каждый 64-й до
512-го и каждый 512-й до 8192-го) дополнительно выводятся на экран, если
shell перестал отвечать.
`enter` без соответствующего `exit` может указывать на зависший вызов;
это не печать всех вызовов на консоль и не изменение поведения Xorg.
Если последний вызов `num=49` (`bind`) не вернулся, дополнительные маркеры
`bind.dispatch` показывают номер fd в старших 32 битах `detail` и семейство
сокета в младших (1 — UNIX, 2 — IPv4). Для UNIX-сокета последовательно
пишутся `bind.unix.enter`, `bind.unix.lookup`, `bind.unix.lookup.done`,
`bind.unix.create`, `bind.unix.create.done`, затем `bind.done`. При создании
пути также отмечаются `bind.unix.vfs.open[.done]` и стадии lwext4
`bind.ext4.fopen[.done]`, `bind.ext4.mode[.done]`,
`bind.ext4.inode[.done]`. Этапы `bind.ext4.*` теперь выводятся только при
создании пути `/.X11-unix/` процессом Xorg: прежняя диагностика ошибочно
расходовала консольный лимит на создание обычных файлов ещё до `bind`.
Последний маркер указывает, внутри какой операции пропал ответ. В `[EXT4WAIT]` поле `io=1` означает активное чтение блока,
`io=2` — запись, `io=0` — вне блочного вызова; `lba` и `sectors` выводятся
только при активном I/O. Эти поля — снимок состояния, не доказательство
исправности диска при `io=0`. Диагностика не изменяет bind или ext4.
Консольный лимит этапов — 24 за загрузку.

Для проверки запускайте сервер в фоне, после паузы читайте
`cat /dev/xorgtrace` **только если shell доступен**. Если после Xorg
зависает и `ls` (Ctrl+C в госте не помогает), не пытайтесь вызывать `cat`
из той же shell: пришлите последние строки консоли `[XORGTRACE]` и
`[EXT4WAIT]`. Последний маркер появляется после двух секунд ожидания
блокировки lwext4 (не более 12 строк за загрузку): `pid`/`tid` — ожидающий,
`owner_pid`/`owner_tid` — владелец, `depth` — глубина рекурсивного захвата.
Его отсутствие **не доказывает**, что ext4 исправна: поток может быть
заблокирован в дисковом вводе-выводе, планировщике или до получения блокировки.
Наличие ожидания также не доказывает причину блокировки владельца.
Если консоль недоступна, сохраните serial-вывод на хосте до завершения VM;
чтение файлов в госте после блокировки shell не требуется.
При запуске QEMU с `-serial stdio` строка `qemu: terminating on signal 2`
означает SIGINT **процессу QEMU на хосте** (например, Ctrl+C в терминале WSL),
а не доказательство аварии ядра BoldonOS. Чтобы видеть полную трассу до
закрытия VM, сохраняйте вывод serial в файл на хосте или фотографируйте
экран VM; Ctrl+C вводите в окно VM, не в терминал QEMU.
Не принимайте единичный `ENOSYS num=141` (`setpriority`) за установленную
причину зависания до просмотра снимка. Трассировка предназначена для
первичной диагностики, не заменяет журнал Xorg и не реализует DRM/KMS.

«Универсальный» драйвер вполне возможен как **один модуль** с общим
DRM/KMS-интерфейсом и таблицей PCI ID, выбирающей код для поддерживаемого
поколения GPU при запуске. Номер CPU заранее не нужен. Но одинаковые
последовательности записи в регистры нельзя применять ко всем Intel HD/UHD:
между поколениями различаются display engine, power wells, PLL, DDI,
прерывания и управление видеопамятью. Неизвестные ID должны безопасно
оставаться на framebuffer Limine. Поддержка широкого набора поколений
наращивается и проверяется поэтапно, без заявления, что любой Intel GPU уже
работает.

Дальнейшие этапы: сначала определить поддержку семейств Intel по PCI ID и
проверить путь запуска Xorg; затем для поддерживаемых поколений разработать
управление режимами, события vblank и переключение буферов с таймаутами и
fallback на Limine. Потом реализовать нужную часть DRM/KMS ABI и проверить
60 Гц, задержки и разрывы на каждом доступном мониторе. Подключение
HDMI/DP/eDP и EDID важны для реального выбора видеорежима и синхронизации,
но не требуются для безопасного PCI-обнаружения.
