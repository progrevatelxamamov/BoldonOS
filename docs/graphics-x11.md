# Графика и Xorg: первый, аппаратно-независимый этап

BoldonOS пока использует framebuffer, полученный от Limine. `/dev/fb0` даёт
прямой доступ к нему; `/dev/dri/card0` сегодня **только старый псевдоним
fbdev**, а не DRM/KMS. В частности `FBIO_WAITFORVSYNC` пока не ждёт
настоящего vblank; нельзя называть этот путь синхронизированным или
гарантировать 60 кадров/с без разрывов.

Для диагностики на любом из ПК: `cat /dev/gpuinfo`. Файл перечисляет все
обнаруженные PCI-видеоконтроллеры (до восьми), выводит BDF, vendor/device ID,
subclass, revision, размер и pitch начального framebuffer. Это **только
чтение PCI config space** и параметров Limine — никаких изменений в GPU,
видеорежиме или в рабочих USB/дисковых драйверах. Список не ограничен
определённой моделью CPU; пустой список возможен и при рабочем framebuffer.

На хосте с **Ubuntu** нет готовой конфигурации репозиториев и ключей Arch
Linux для `pacman`: одной установкой `pacman` через apt это не исправить.
Если нужен именно Arch Xorg в `osdata/`, можно использовать Arch-контейнер
(требуются Docker и доступ к образу `archlinux:latest`). Перед этим
сохраните резервную копию существующего `osdata` — установка пакетов может
конфликтовать с уже положенными туда файлами. В WSL запускайте установку
из файловой системы Linux (например, `~/BoldonOS`), **не** из `/mnt/c/...`:
Windows-раздел через DrvFs может показывать каталоги как `777`, игнорировать
нужные Unix-права и вызывать тысячи предупреждений pacman `filesystem: 777,
package: 755`. Хуже того, при регистронезависимой настройке NTFS пути
`/usr/lib/Xorg` (исполняемый файл) и `/usr/lib/xorg` (каталог модулей)
совпадают: установка завершается `not overwriting dir with file` и не может
быть исправлена `--overwrite '*'` или удалением каталога модулей. Проверка:
`stat -c '%i %n' osdata/usr/lib/Xorg osdata/usr/lib/xorg` покажет одинаковый
inode в случае коллизии. Перенесите рабочую копию вместе с `osdata` на
файловую систему Linux внутри WSL перед повторной установкой. Уже
скопированные из DrvFs права могут оставаться неверными — проверяйте их
отдельно. `main.img` копирует права из дерева, поэтому одного подавления
предупреждений недостаточно. Для уже установленного дерева
сначала проверьте результат и права, не применяйте `chmod -R 755` (это
сломает, например, `/tmp` и обычные файлы).


```sh
mkdir -p osdata/var/lib/pacman osdata/var/log
sudo docker run --rm -it -v "$PWD/osdata:/rootfs" archlinux:latest sh -ec '
  pacman --root /rootfs --dbpath /rootfs/var/lib/pacman \
    --logfile /rootfs/var/log/pacman.log --config /etc/pacman.conf \
    --gpgdir /etc/pacman.d/gnupg --cachedir /var/cache/pacman/pkg \
    -Syu --needed xorg-server xorg-xinit xf86-video-fbdev xf86-input-evdev xterm
'
```

`-it` сохраняет терминал и ввод для подтверждения `[Y/n]`: без `-i`
`pacman` получит EOF и выйдет, не установив пакеты. `--root` направляет
файлы в `osdata/`; явные `--dbpath` и `--logfile` гарантируют, что база и
журнал также останутся в нём, а не в контейнере. `--cachedir` хранит архивы
только внутри временного контейнера. Перед подтверждением списка обновлений
проверьте `osdata/var/lib/pacman/local`: если каталог пустой, но pacman
показывает *старые версии* системных пакетов, не подтверждайте установку —
проверьте путь базы пакетов. Не применяйте `--overwrite '*'` для разрешения
конфликтов с существующими файлами. Сборка `main.img` копирует `osdata/` в
ext4 при **новой сборке** образа (не изменяет готовый образ); проверьте,
что в разделе хватает места для пакетов. Это способ подготовки бинарников,
а не готовый установщик или гарантия работоспособности Xorg в BoldonOS.

**Установка не означает, что Xorg уже запустится.** `startxfce4` и
`/etc/X11/xinit/xserverrc` — shell-скрипты с `#!`: `execve` должен передавать
их интерпретатору. Раньше ядро принимало только ELF, а системный вызов
ошибочно превращал все ошибки `execve` в `EPERM` («Operation not permitted»).
После поддержки скриптов ошибки Xorg нужно диагностировать по настоящему
коду возврата и его журналу; исправление `execve` само по себе не добавляет
DRM/KMS. Это бинарники Arch Linux,
а не портированный X-сервер: они зависят от ABI Linux, динамического
загрузчика, поддерживаемых системных вызовов, устройств ввода и корректных
fbdev/DRM ioctl. Драйвер `xf86-video-fbdev` — лишь программный запасной
вариант, не обеспечивает KMS, аппаратную акселерацию и vsync. Если сервер
выбирает `/dev/dri/card0` как настоящий DRM-узел, он получит несовместимые
ioctl; его нельзя считать реализацией DRM.

«Универсальный» драйвер вполне возможен как **один модуль** с общим
DRM/KMS-интерфейсом и таблицей PCI ID, выбирающей код для поддерживаемого
поколения GPU при запуске. Номер CPU заранее не нужен. Но одинаковые
последовательности записи в регистры нельзя применять ко всем Intel HD/UHD:
между поколениями различаются display engine, power wells, PLL, DDI,
прерывания и управление видеопамятью. Неизвестные ID должны безопасно
оставаться на framebuffer Limine. Поддержка широкого набора поколений
наращивается и проверяется поэтапно, без заявления, что любой Intel GPU уже
работает.

Дальнейшие этапы: сначала определить поддержку семейств Intel по PCI ID и
проверить путь запуска Xorg; затем для поддерживаемых поколений разработать
управление режимами, события vblank и переключение буферов с таймаутами и
fallback на Limine. Потом реализовать нужную часть DRM/KMS ABI и проверить
60 Гц, задержки и разрывы на каждом доступном мониторе. Подключение
HDMI/DP/eDP и EDID важны для реального выбора видеорежима и синхронизации,
но не требуются для безопасного PCI-обнаружения.
